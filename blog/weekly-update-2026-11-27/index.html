Limitcast weekly update, Nov 27 — six starts, one slot

Sam Stull · 27 November 2026

If you set a cap of one Explore subagent per session, six parallel requests should still use just one slot. Limitcast 0.20.10 fixes the race that could let several requests through together. The patch is now available on GitHub and npm.

What happened when six requests arrived together

In 0.20.9, the guard could let two hook processes read the same count before either reserved a slot. The guard now checks and reserves the slot in one operation. It counts requests as it admits them, so a missing or delayed usage receipt cannot free a slot.

We sent six synthetic requests for the same subagent type in one session, using the event format for each host. The test ran the guard from the published npm package directly. 

Claude Code   1 admitted, 5 held
Codex         1 admitted, 5 held
Grok          1 admitted, 5 held

This measures the guard’s decisions in a controlled test. Your host needs its guard hook installed and active to enforce a cap in a live session.

Set a cap for one subagent type

On Node.js 22 or later, install the patch, enable the guard and set a cap for the type you want to limit. The cap is opt-in and applies within each session. 

npm install -g limitcast@0.20.10
limitcast install --guard
limitcast budget type explore 1

Restart your host to load the hook. In Codex, approve the hook when prompted. To read the saved cap, run limitcast budget type explore.

What should a hold tell you?

When the cap holds a start, would you rather see which earlier starts used your slots in the hold message, or look them up with a command afterward?
